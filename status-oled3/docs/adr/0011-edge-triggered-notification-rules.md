# 11. 服务探活 / 未读邮件 / 停更提示音的「上升沿一次性」规则

日期：2026-10-16

## 状态

已接受

## 背景

[ADR-0003](0003-active-buzzer-on-off-encoding.md) 定了蜂鸣器的编码方式（通断时长）与初版节奏表：新未读邮件 = 短响 1 次；服务器停更超时 = 连续短响 3 次；WiFi 断开 = 长响 1 次；按钮空操作 = 极短响 1 次。

到 M2 真实触发这三类事件时，出现一个必须回答的问题：**什么算「一次事件」**。轮询是 15 秒一次的周期行为，如果不定义触发条件，最直观的实现（「每次轮询发现停更就响」）会让蜂鸣器每 15 秒响一次——那不是通知，是折磨。

## 考虑的方案

### 方案 A：全部按状态上升沿触发，一次性 —— 采纳

记录上一次的状态，只在「状态从好变坏」或「指标上升」的那一个轮询周期触发提示音，之后保持静默，直到状态恢复后再次变坏才重新触发。

| 事件 | 触发条件 | 不触发 |
|---|---|---|
| 新未读邮件 | 未读总数**上升**（`unread > prevUnread`） | 未读不变、未读下降（用户自己去读了邮件） |
| 服务器停更 | 进入停更态的那一瞬（`!stale && stale`） | 持续停更的每一个周期 |
| WiFi 断开 | `online` 变为 `offline` 的那一瞬 | 重连过程中、持续离线 |

**采纳理由**：

1. **通知的语义就是「有变化」**：桌面显示器的价值在于用户不必盯着屏幕。持续停更在屏幕上已经持续可见，蜂鸣器再重复响没有增加信息，只增加噪音。
2. **未读「上升沿」而非「非零」**：非零判定会让「有 3 封未读」这件事每 15 秒响一次。上升沿只在新邮件到达时响一次，与「通知」的直觉一致。
3. **未读下降不响**：用户在别处读掉了邮件，设备屏幕的数字会跟着降——这是正常状态变化，不需要提示音。若给它也配音，读邮件本身会变成噪音源。
4. **停更恢复不响**：[ADR-0003](0003-active-buzzer-on-off-encoding.md) 的节奏表里没有「恢复」这一项，且恢复是好消息而非异常。屏幕上的数字自己会回来，够了。

### 方案 B：每次轮询发现异常就响

**否决理由**：15 秒一次的重响在停更场景下（服务器宕机可能持续数小时）完全不可用。且阻塞式蜂鸣器每次占用 3×80ms+2×120ms = 480ms，会实打实推迟 I2C flush。

### 方案 C：停更按固定间隔重复提醒（例如每 5 分钟响一次）

**否决理由**：需要额外的计时状态，而屏幕已经持续显示停更态；用户抬头看一眼就知道。为「防止用户一直没抬头」付 5 分钟的定时噪音，收益不成立。

## 决策

在 `main.cpp` 维护三个「上一次」状态，与当前状态比较产生上升沿：

```cpp
static bool     prevNetOnline  = true;   // WiFi
static bool     prevStale      = false;  // server data
static uint32_t prevUnread     = 0;      // mailbox
```

- 三个上升沿各自触发一次对应节奏，**同一周期内多个上升沿同时发生时按「新邮件 → 停更 → 断网」的顺序串行播放**（`buzzer` 是阻塞式的，见下）。
- 首次上电时 `prevNetOnline = true`、`prevStale = false`、`prevUnread = 0`，即**上电不因「初始状态」触发任何提示音**（否则每次重启都会无缘无故响一遍）。`prevUnread` 需要在 M1a 的第一次成功拉取后被赋为实际值而不是 0，否则「从 0 变成 7」会被误判成一次新邮件——这是本决策最容易踩的坑。
- 按钮空操作的极短响（`patternButtonEmpty`）**不走上升沿**：它是对用户操作的即时反馈，每次空操作都该响，语义与前三者不同。

## 后果

### 正面

- 停更再长也只响一次，蜂鸣器不会变成噪音源。
- 每条提示音都对应一个用户可理解的「刚刚发生了什么」。
- 实现只需三个变量，无定时器、无队列。

### 负面 / 需承担的成本

1. **阻塞式蜂鸣器与上升沿播放叠加时的卡顿**：`buzzer.h` 文件头已记录该取舍——`patternServerStale()` 占用 3×80ms + 2×120ms = 480ms，期间 `loop()` 停转，I2C flush 被推迟。若实测可见卡顿（按钮响应迟钝、屏幕刷新抖动），按 `buzzer.h` 记录的迁移路径改成 `tick()` 驱动的非阻塞序列；**该改动只动 `buzzer.*`，不动本决策的上升沿逻辑**。
2. **用户可能错过唯一一次提示音**：响一次就静默意味着当时不在桌前就错过了。补偿是屏幕上的状态持续可见（停更标记、未读数字），蜂鸣器不是唯一通道——这是桌面显示器的定位，不是报警器。
3. **`prevUnread` 的初值陷阱**：见上文，第一次成功拉取后必须立即把 `prevUnread` 同步为实际值。这条要在代码里显式注释，否则重构时极易被改回去。

## 备注

- 本决策只管「何时响」，不管「响多长」——后者是 [ADR-0003](0003-active-buzzer-on-off-encoding.md) 的节奏表。
- M1a 阶段只实现「停更」与「WiFi 断开」两个上升沿（未读数要等 M1b）；三个变量的结构先建好，避免 M1b 再改一轮。

## 落地记录（2026-10-17，M1b 固件）

未读上升沿已实现，但**没有按上面伪代码的「单槽 `prevUnread`」写**，而是改成「双槽一次轮询滞后」：

```cpp
// health.cpp 匿名 namespace
bool     g_unread_prev_known = false;  long g_unread_prev = 0;  // poll N-1
bool     g_unread_last_known = false;  long g_unread_last = 0;  // poll N
```

每次成功 mailbox 轮询做 `prev ← last; last ← new`，`unreadRose()` = `last_known && prev_known && last > prev`。

**为什么偏离伪代码**：`health.h` 要求 `unreadRose()` 是「查询」而不是「存储标志」，调用方错过下一次轮询仍应能看到同一次上升沿。单槽方案在轮询处就地把 `prev` 更新掉，上升沿只在轮询后的一个 `loop()` 迭代内可见，而 `loop()` 里有阻塞蜂鸣器与 I2C flush——恰好是最容易错过的那一瞬。双槽让上升沿在整个 5 分钟邮箱轮询窗口内稳定为真，由 `main.cpp` 自己 latch（`g_announced_rose`）去重。

**ADR-0011:53 的 `prevUnread` 初值陷阱由结构天然满足**：首次拉取时 `prev_known == false`，`last > prev` 不成立，不会把「0 → 7」误判成新邮件；第一次轮询后 `prev` 被同步为实际值。`unread` 变 `null`（IMAP 连不上）时 `last_known = false`，下次恢复时 `prev_known` 同样为 false，**不会产生幽灵沿**——这是单槽方案要靠额外分支才能保证的。

`main.cpp` 的三个 `prev` 变量仍按本决策的初值设置（`prevNetOnline = true` / `prevStale = false`），上电自身不触发提示音的逻辑不变。
