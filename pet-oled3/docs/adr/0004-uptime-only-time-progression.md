# 4. 仅开机时间推进，关机暂停

日期：2026-10-15

## 状态

已接受

## 背景

养成游戏的核心是"角色状态随时间演变"。时间的定义方式决定了：需要什么硬件、掉电后发生什么、以及代码复杂度。

本仓库已有联网对时的先例（`clock-oled` 用 NTP），因此"要不要联网"是个真实的选项，不是假想。

## 考虑的方案

### 方案 A：真实时间推进（带离线成长）

角色在设备关机期间也继续变化（饱食度继续掉），重启后按真实时间补算。

**否决理由**：

1. **必须知道"现在几点"**，而 ESP32-S3 没有电池备份的 RTC。掉电后时间归零，所以要么**联网 NTP 对时**，要么**外接 RTC 模块**——两者都是额外依赖。
2. **联网的代价已实测**。`../../../HARDWARE.md:343-344` 记录 `clock-oled` 的 RAM 占用 **14.1%**、Flash 占用 **21.5%**，且明确注明"全部来自 libWiFi 协议栈（联网对时的必然代价）"。为时间推进支付这个代价，对一个纯本地小游戏不成比例。
3. **离线成长会带来糟糕的玩法体验**。玩家关机一天再打开，发现角色已经饿到濒死——这是惩罚玩家不玩游戏，与养成游戏"陪伴感"的立意相反。真要做得好看，需要设计离线衰减上限、回归补偿等一整套机制。

### 方案 B：开机推进 + NVS 存档续时

开机只算运行时间，但用 ESP32 的 NVS 存一份时间戳，重启后能恢复"上次玩到哪"，不联网也能大致续上。

**否决理由**：这实际上是在用 NVS 模拟一个不精确的 RTC。它引入了方案 A 的部分复杂度（时间戳的存储、校验、跨重启的一致性），却只换来一个"大致续上"的模糊结果。**如果要做时间持久化，就该认真做（NVS 存完整游戏状态）；如果只是推进游戏时间，就不需要它。** 两者是不同的需求，本方案选择后者。

### 方案 C：仅开机时间推进 —— 采纳

用 `millis()` 累积游戏时间，关机/复位即从零开始。

**采纳理由**：

1. **零额外依赖**：不联网、不接 RTC、不用 NVS
2. **规避 WiFi 协议栈开销**：省下 14.1% RAM / 21.5% Flash（`../../../HARDWARE.md:343-344`）
3. **时间流速恒定可测**。基于 `millis()` 的游戏 tick 是确定性的，容易写测试、容易复现 bug
4. **调试简单**。不需要处理"设备没联网时怎么办"分支
5. **它符合本设备的形态**。这是一个**掌上设备**，玩家玩它的时候它开着。游戏时间只在玩家在场时流逝，符合直觉
6. **开发顺序上它是 bringup 友好的**：M0/M1（硬件验证）完全不需要时间概念，M3 才引入 tick

## 决策

**游戏时间仅由 `millis()` 在开机运行期间累积，关机暂停，无持久化。**

明确**不做**：联网 NTP、外置 RTC、NVS 时间戳续时、离线成长。

## 后果

### 正面

- 无 WiFi 栈开销（RAM/Flash 大幅节省）
- 无外部器件
- tick 确定性，可测可复现
- 无"设备没联网"的降级分支

### 负面 / 需承担的成本

1. **没有离线成长**。玩家关机期间的进度完全不计。可能被部分玩家视为"关机就白养"——**这是本决策已知且接受的代价**
2. **重启即重来**。不小心按到复位键，当前进度全部丢失，且没有存档
3. **成长阶段阈值必须适应"单次开机时长"**。若一次游玩平均 30 分钟，那么"存活 > 2 小时"的衰老阈值几乎不可达，需要在数值平衡阶段重新校准（见 [`../策划案.md`](../策划案.md) §7）

### 未来扩展路径（未排期）

若日后确需持久化，正确做法是**用 NVS 存完整游戏状态**（三条数值 + 亲密度 + 存活时长 + 阶段），而不是存时间戳去补算。这样可以精确恢复，且不引入"离线期间发生了什么"的模拟问题。

## 备注

- `millis()` 本身有精度限制（`unsigned long` 回绕约 49.7 天），但对"仅开机推进"的掌上设备不构成实际问题
- 本决策使 `clock-oled` 的联网资产在本项目中**不适用**，仅作参考
