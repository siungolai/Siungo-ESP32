# 5. bringup 优先：先验通三屏，再写游戏

日期：2026-10-15

## 状态

已接受

## 背景

本项目有两块独立的风险：

1. **硬件风险**：PCA9548A + 三块屏这条链路从未在本机验证过。未知项包括 PCA9548A 的实际地址、通道切换是否生效、三块屏能否分别点亮、多通道下的电平是否可靠。
2. **软件风险**：游戏逻辑本身（三条数值的联动、成长状态机、输入处理）。

这两块风险的**验证成本差异极大**：硬件问题只能靠实物验证，且一旦拓扑假设错误，会推翻大量上层代码。因此开发顺序本身是一个需要决策的问题。

## 考虑的方案

### 方案 A：先 bringup 验证三屏，再写游戏 —— 采纳

先写一个**最小验证项目**（M0），只做一件事：证明 PCA9548A + 三块屏这条链路真的通。硬件通了再开始写游戏。

**采纳理由**：

1. **前置消灭最贵的风险**。硬件拓扑一旦假设错误（例如 PCA9548A 实际地址不是 0x70、或键盘实为 I2C 编码型改变了拓扑），受影响的是**整个上层架构**。越早发现越便宜。
2. **bringup 的验收标准是客观的**：三块屏能显示三个不同的字符串，且单独刷新其中一块不干扰另外两块。这比"游戏好不好玩"可验证得多。
3. **它产出可复用的资产**。bringup 项目里的 PCA9548A 驱动、通道探测逻辑、诊断输出，**全部是后续游戏项目的直接依赖**，不是一次性丢弃的代码。
4. **当前正是做这件事的时机**。用户已购 PCA9548A 但尚未接线，硬件是全新的、未验证的。
5. **它让未知项显性化**。[`../策划案.md`](../策划案.md) §7 的待验证清单中，第 1、2、5 项（PCA9548A 地址、模块上拉位置、键盘类型）**必须在 bringup 期间确认**，否则它们会以"隐性假设"的形式污染整个设计。

### 方案 B：先写游戏内核，后接三屏

先写游戏逻辑（数值、状态机、输入），屏幕先用单屏或串口日志代替，最后再接三屏。

**否决理由**：

1. **它把最高风险推到最后**。若 bringup 阶段发现拓扑假设错误，此时已经写完了大量依赖该假设的游戏代码。
2. **它基于一个未验证的假设工作**：即"三块屏一定能按预期工作"。而这个假设**恰恰是当前最大的未知**。
3. 该方案的宣传优点"开发期不用等硬件"在本项目中**不成立**——硬件已经在手上（用户已购 PCA9548A），不存在等待。

### 方案 C：两条并行

bringup 与游戏内核并行开发，策划案里给并行里程碑。

**否决理由**：

1. 本项目是**单人开发**，并行不会缩短总工期，只会增加"两边都要维护"的上下文切换成本。
2. **接口尚未冻结**。游戏内核与显示层的接口（`Display` 类如何暴露通道、刷新调度的调用约定）依赖 bringup 的结论。在接口未定时并行开发，等于先写一遍再改一遍。
3. bringup 本身工作量很小（一个最小项目 + 约 50 行驱动），**串行执行的成本低于协调并行的成本**。

## 决策

**开发路径为串行：M0 bringup 优先，作为 M1 及之后所有里程碑的阻塞前置。**

M0 的验收标准（见 [`../策划案.md`](../策划案.md) §6）：

- 扫描确认 PCA9548A 实际地址（以扫描结果为准，不硬编码 0x70）
- `select()` / `deselect_all()` 生效验证
- 逐通道探测通道 0/1/2 上的 0x3C
- **三块屏分别显示不同内容**（同内容无法区分是否真的切换成功）
- 确认 GPIO 分配表在本机可用
- 更新 `../../../HARDWARE.md`

## 后果

### 正面

- 最贵的风险最早暴露
- bringup 产出的驱动与诊断代码直接复用
- 游戏开发建立在一个已验证的硬件基础上
- 待验证清单中的关键项在 M0 就被消灭，不会带病进入设计

### 负面 / 需承担的成本

1. **前期"看不到游戏"**。M0 阶段没有游戏内容，只有硬件验证输出。需要接受这个心理成本
2. **bringup 可能推翻已写的策划案章节**。若证实 PCA9548A 地址不是 0x70、或键盘是 I2C 编码型，策划案的接线表需要修订——**这是好事，说明它暴露得足够早**
3. 里程碑顺序上是严格串行，没有并行加速的空间

## 备注

- bringup 的验证方法参考仓库已有的 `pin-probe` 项目（I2C 扫描 + 引脚探测工具）
- 若 M0 阶段发现 PCA9548A 模块的上拉是"八路全挂"型，会直接触发 [ADR-0002](0002-single-channel-sequential-refresh.md) 中记录的上拉并联风险评估，需要实测低电平余量
