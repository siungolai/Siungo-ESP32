# CONTEXT · 术语表

本项目的**唯一术语来源**。文档、代码、注释、提交信息统一使用本表命名的词。
同义词在「不要叫」列中列出，出现即视为需要修正。

维护规则：**新增概念时才新增条目**；纯实现细节不进本表。

---

## 硬件层

### 上游（Upstream）

| 项 | 内容 |
|---|---|
| 含义 | ESP32-S3 与 PCA9548A 之间那一段 I2C 总线 |
| 不要叫 | 主总线、main bus、一级总线 |
| 出处 | [`docs/策划案.md` §2.2](docs/策划案.md) |

> 用「上游/下游」而非「主/从」，因为「主从」在本项目里已经用于 I2C 的 master/slave 语义，混用会歧义。

### 下游 / 通道（Channel）

| 项 | 内容 |
|---|---|
| 含义 | PCA9548A 的 8 路开关之一，以及它引出的那段独立 I2C 支路 |
| 命名 | `通道 0` … `通道 7`，代码中 `channel 0` … `channel 7` |
| 不要叫 | port、口、路、branch |
| 出处 | [`docs/策划案.md` §3.2](docs/策划案.md) |

### 选通 / 断开（Select / Deselect）

| 项 | 内容 |
|---|---|
| 含义 | 把某个通道的开关闭合（选通）或断开（断开） |
| 代码 | `pca9548a::select(n)` / `pca9548a::deselectAll()` |
| 不要叫 | 打开/关闭（歧义：打开开关 ≠ 打开通道）、enable/disable |
| 出处 | [`docs/策划案.md` §5.2](docs/策划案.md) |

> 刻意避开「打开/关闭」——中文里「打开通道」可能是"接通"也可能是"断开"，必须用无歧义的「选通/断开」。
>
> 📌 代码名以 `status-oled3/src/pca9548a.h` 为准（命名空间 `pca9548a`）。本项目直接复用该驱动，**不要再抄一份签名**。

### 三屏角色（Screen Role）

本项目**不叫**「屏 1/屏 2/屏 3」，因为数字编号无法表达职责。统一用角色名：

| 术语 | 通道 | 职责 | 不要叫 |
|---|---|---|---|
| **角色屏** | 通道 0 | 角色大图 + 表情 | 主屏、屏 1、screen A |
| **数值屏** | 通道 1 | 三条数值条 + 数字 | 副屏、屏 2、screen B |
| **日志屏** | 通道 2 | 事件滚动、菜单、提示 | 状态屏、屏 3、screen C |

> 需要指物理位置时才用「屏 1/2/3」，且必须紧跟角色名，如「角色屏（屏 1）」。

### 刷新优先级（Refresh Priority）

| 项 | 内容 |
|---|---|
| 含义 | 轮询时的检查顺序：**日志 → 数值 → 角色** |
| 理由 | 按信息变化频率分层，变化最快的优先 |
| 不要叫 | 刷新顺序、poll order |
| 出处 | [`docs/策划案.md` §5.4](docs/策划案.md) |

### 掉屏（Screen Absent）

| 项 | 内容 |
|---|---|
| 含义 | 某通道上的屏不在线（无应答） |
| 处置 | 该通道 `flush()` **立即返回，不产生任何 I2C 事务** |
| 理由 | 否则每次 `endTransmission()` 阻塞 50ms，一轮 8 页 ≈ 800ms，拖垮节拍 |
| 出处 | [`HARDWARE.md`](../HARDWARE.md) §6.2、[`docs/策划案.md` §5.3](docs/策划案.md) |

> 与 I2C 的「无应答」区分：**掉屏**是应用层的状态判断（这块屏归零了），「无应答」是单次事务的结果码。

## 游戏层

### 数值（Stat）

三条互相牵制的属性，**统称「三条数值」**，不要叫「属性」「参数」「指标」。

| 术语 | 含义 | 下降 | 回升 |
|---|---|---|---|
| **饱食度** | 饿不饿 | 持续 | 喂食 |
| **心情** | 开不开心 | 中期 | 玩耍 |
| **体力** | 累不累 | 玩耍时加速 | 休息 |

> 英文名（代码用）**仍未定稿**。M0 固件在数值屏上显示的 `food` / `mood` / `energy` / `aff` 是**屏幕上的短标签**（5×7 点阵放不下中文，且 M0 只显示静态初值），**不等于代码里的正式标识符**。M3 真正实现三条数值逻辑前必须先定英文名，**不要**在未确认前自行发明英文标识符。
>
> 📌 **数值口径已定稿**（2026-10-21 脚本核验，[`docs/策划案.md` §4.6](docs/策划案.md)）：范围 [0,100]，初值 **饱食 70 / 心情 70 / 体力 80**；三条**同速衰减 12 点/小时**；**告警阈值 30**；喂食 +25 / 玩耍 心情+20 饱食−5 体力−5 / 休息 体力+25 心情−2；动作冷却 30 秒。决策依据见 [ADR-0008](docs/adr/0008-numeric-balance-first-pass-parameters.md)。
>
> ⚠️ **「玩法层的下降」与「衰减速率」是两回事**——三条数值**同速衰减**，「心情中期下降、体力玩耍时加速」说的是**动作副作用**造成的策略差异，不是三套衰减率。

### 冷落（Neglect）

| 项 | 内容 |
|---|---|
| 含义 | **三条数值中任一条 < 30** 的状态 |
| 后果 | **只加速亲密度衰减（×3）**，三条数值照常衰减 |
| 数值 | 与「告警阈值 30」**是同一个 30**——一个数，两个用途 |
| 不要叫 | 饥饿、虚弱（那是单条数值的低，不是整体状态） |
| 出处 | [`docs/策划案.md` §4.2](docs/策划案.md)、[ADR-0008](docs/adr/0008-numeric-balance-first-pass-parameters.md) |

> 📌 **冷落不加速三条数值的衰减**——这是刻意的设计决定。若一起加速，跌破 30 后玩家越救越救不回来（死亡螺旋），参数搜索无解。

### 主动作（Action）

玩家对角色施加的三个操作，**恰好三个**：

| 术语 | 怎么触发 | 主效果 | 副作用 |
|---|---|---|---|
| **喂食** | 主界面光标移到「喂食」→ 按 B 确认 | 饱食度 ↑ | 过饱掉心情 |
| **玩耍** | 主界面光标移到「玩耍」→ 按 B 确认 | 心情 ↑ | 消耗体力 |
| **休息** | 主界面光标移到「休息」→ 按 B 确认 | 体力 ↑ | 心情缓降 |

> 「主动作」是为了和「游戏 tick」（被动推进）区分。
>
> 📌 **三个主动作没有各自的物理按键**。硬件只有两个按钮（[ADR-0007](docs/adr/0007-two-buttons-only-input.md)），三个动作是主界面光标的三个选项。

### 按钮（Button）

| 项 | 内容 |
|---|---|
| 器件 | 轻触开关 ×2，**内部上拉**，按下接地为低电平 |
| 编号 | **按钮 A = GPIO 6**（选动作 / 光标下移）、**按钮 B = GPIO 7**（确认 / 执行） |
| 事件 | 短按（释放时发一次）、长按（跨过 1000 ms 阈值时发一次，释放不补发） |
| 消抖 | 4 态状态机，按压与释放各采样，须持续满 **20 ms** |
| 不要叫 | 键 1 / 键 2 / 键 3（那是初版键盘方案的遗留，键盘已取消） |
| 出处 | [ADR-0007](docs/adr/0007-two-buttons-only-input.md)、[`docs/策划案.md` §4.4](docs/策划案.md) |

### 上下文（Context）

| 项 | 内容 |
|---|---|
| 含义 | 按钮含义随当前界面状态改变的那个"模式" |
| 两种 | **主界面**（选主动作）、**菜单**（光标下移 + 确认） |
| 退出 | **长按按钮 B** 返回上一级（两键方案没有第三个键） |
| 不要叫 | 模式、页面、界面状态（"mode" 与"上下文"混用会与游戏模式冲突） |
| 出处 | [ADR-0007](docs/adr/0007-two-buttons-only-input.md)、[ADR-0009](docs/adr/0009-two-button-interaction-coverage.md) |

> 📌 **菜单只有两项**（静音开关 / 关于本机），**没有「数值调校」项**——数值调参已移出运行时 UI，走编译期常量（静音走 NVS）。**菜单不引入第三个上下文**。
>
> 📌 **手势矩阵 = `2 上下文 × 2 键 × 2 按压型 = 8 种组合`，全部有归属**（无「其他」）：**6 种已绑定**、**2 种明确不绑定**（主界面长按 B、菜单长按 A）。完整交互面见 [ADR-0009](docs/adr/0009-two-button-interaction-coverage.md)。

### 光标（Cursor）

| 项 | 内容 |
|---|---|
| 含义 | 主界面里指向当前主动作的高亮项 |
| 行为 | 按 A 在 **喂食 / 玩耍 / 休息** 之间循环；**执行动作后光标不动**（便于连续喂食） |
| 默认位置 | 角色屏（通道 0） |
| 出处 | [`docs/策划案.md` §4.4](docs/策划案.md) |

### tick

| 项 | 内容 |
|---|---|
| 含义 | 游戏逻辑的一次时间推进（1 Hz） |
| 特性 | 基于 `millis()`，**与屏幕在线状态完全解耦** |
| 不要叫 | 帧、frame、loop（那是刷新层的概念） |
| 出处 | [`docs/策划案.md` §5.3](docs/策划案.md) |

> **tick ≠ frame**。tick 是逻辑时间，frame 是显示刷新。三块屏各有各的 frame 频率，但共享同一个 tick。
>
> ⚠️ **tick 里的衰减必须用定点余数累加**（毫点为单位），不能写成 `value -= 12/60`——那样整数取整后每秒减 0，数值永远不降。见 [`docs/策划案.md` §4.6.5](docs/策划案.md)。

### 成长阶段（Stage）

| 阶段 | 进入条件 |
|---|---|
| **卵** | 初始 |
| **幼体** | 存活 > 5 分钟 |
| **成体** | 存活 > 30 分钟 且 **亲密度 ≥ 15** |
| **衰老** | 存活 > 2 小时 |

> ✅ **亲密度门槛 15 已定稿**（2026-10-21 脚本核验，[`docs/策划案.md` §4.3](docs/策划案.md)）。这个值**有区分度**：勤快玩家 30 分钟时亲密度 17.5（已达成成体），守候玩家 30 分钟时 8.5（未达成）。决策依据见 [ADR-0008](docs/adr/0008-numeric-balance-first-pass-parameters.md)。
>
> 📌 **5 分钟 / 30 分钟 / 2 小时这三个时间阈值仍是待调数值**（**§7 第 10 项已结案：数值参数首版定稿，脚本核验通过**；这三个时间阈值本身仍属于 M4 的手感调优范围），**只有亲密度门槛 15 是定稿的**。

### 亲密度

| 项 | 内容 |
|---|---|
| 含义 | 长期互动的累积值，与三条数值不同（衰减极缓） |
| 作用 | 成长阶段的判定条件之一 |
| 数值口径 | 范围 [0,100]，初值 0；正常照看衰减 **1 点/小时**，**冷落时 ×3**（冷落 = 三条数值任一 < 30） |
| 不要叫 | 好感度、经验（那是 RPG 词汇，本项目不用） |

> 📌 亲密度**会下降**，不是只涨——但远缓于三条数值（正常 100 小时归零，冷落 33.3 小时归零）。完整口径见 [`docs/策划案.md` §4.6](docs/策划案.md)。

### 时间推进（Time Progression）

| 项 | 内容 |
|---|---|
| 含义 | **仅开机时间推进，关机暂停** |
| 不要叫 | 离线成长（那是**被明确否决**的方案） |
| 出处 | [ADR-0004](docs/adr/0004-uptime-only-time-progression.md) |

## 开发层

### bringup

| 项 | 内容 |
|---|---|
| 含义 | 硬件通路的首次验证项目（M0），在写游戏前完成 |
| 目的 | 证明 PCA9548A + 三块屏这条链路真的通 |
| 不要叫 | 冒烟测试、smoke test（bringup 范围更大，含地址探测与通道验证） |
| 状态 | ✅ **2026-10-21 已完成**（M0 固件 `pet-oled3/src/main.cpp` 上板实测通过：0x70 应答、三通道全 ACK、三屏各显各内容、四种按钮手势全触发、蜂鸣器驱动档读回 = 3）。结案记录见 [`策划案.md`](docs/策划案.md) §6/§7/§10 与 [ADR-0005](docs/adr/0005-bringup-first.md) |
| 出处 | [ADR-0005](docs/adr/0005-bringup-first.md) |

### 硬约束（Hard Constraint）

本仓库**实测得出、不可协商**的接线禁忌。违反即硬件不工作：

| # | 约束 | 依据 |
|---|---|---|
| 1 | I2C **禁止**接 GPIO 1 / GPIO 2 | [`HARDWARE.md`](../HARDWARE.md) §6.1（全段超时） |
| 2 | **禁止**占用 GPIO 19 / 20 | 原生 USB，占则失串口 |
| 3 | **禁止**往 SDA/SCL 重复加 4.7k 上拉 | 上下游均已有上拉，并联过载 |
| 4 | I2C **SDA/SCL 线序不可交换**（GPIO5→SDA、GPIO4→SCL） | [`HARDWARE.md`](../HARDWARE.md) §4.5（电气全正常但无器件应答，36h 排查） |
| 5 | **禁止**占用 GPIO 38（除非加第三键） | 现为保留空闲脚（[ADR-0007](docs/adr/0007-two-buttons-only-input.md)） |
| 6 | **禁止**占用 GPIO 0 / 3 / 45 / 46（strapping 脚） | ESP32-S3 datasheet v2.2 §2.3.4 / §3；上电电平参与 boot mode 与 VDD_SPI 电压判定。**注意 MTDI 是 GPIO 41 不是 GPIO 12，GPIO 12 是普通 IO** |
| 7 | **禁止**在 GPIO 7 上同时接 DHT11 数据脚 | 与 `dht11-oled` 二选一（[`HARDWARE.md`](../HARDWARE.md) §1.2）；DHT11 自带上拉会与按钮内部上拉并联 |

> 这些叫「硬约束」不叫「注意事项」——"注意"是软的，这些是硬的。
>
> 📌 约束 4 最反直觉：接反了**电气指标全部正常**（idle HIGH/HIGH、上拉在线、无超时），但没有任何器件应答。**0x70 不应答时先查线序。**
