# uptime-oled · 128x64 I2C OLED 通电计时器

上电即开始计时，**每 1 秒**刷新一次屏幕，显示本次通电以来跑了多久。挂在 **SSD1306**（128x64 I2C OLED）上。

## 接线

| OLED 排针 | ESP32-S3 |
|---|---|
| SCL（时钟线） | **GPIO 4** |
| SDA（数据线） | **GPIO 5** |
| VCC | 3V3 |
| GND | GND |

> 时钟线接 4 号位、数据线接 5 号位。
> 引脚编号写在 `src/main.cpp` 顶部的 `PIN_I2C_SCL` / `PIN_I2C_SDA`，换脚只改这两行。
> ESP32 的 `Wire.begin(sda, scl, freq)` 允许指定任意 GPIO，所以不需要 `Wire.setPins()`，也不需要改 `platformio.ini`。
>
> 2026-10-14：原先接 GPIO1/2 时总线完全不通（详见文末实测记录），改到 GPIO4/5 后正常点亮。

**SCL 与 SDA 接反是最常见的不显示原因**：模块会完全无应答，串口自检会直接报出来。

## 屏幕布局

```
┌────────────────────────────────┐
│ UPTIME                   #123  │  ← 第 0 页：标题 + 刷新计数
│ ────────────────────────────── │  ← 第 1 页：分隔线
│   ██  ██   ██ ██               │
│   ██  ██   ██ ██               │  ← 第 2~3 页：2 倍放大主数值 MM:SS
│                                │
│ 00:02:03                       │  ← 第 5 页：HH:MM:SS 完整分解
│ TOTAL 123 s                    │  ← 第 6 页：总秒数
│ ████████████░░░░░░░░░░░░░░░░░░ │  ← 第 7 页：60 秒一圈的进度条
└────────────────────────────────┘
```

- **`#123` 刷新计数**：每刷一帧 +1。它就是"1 秒更新一次"的**现场证据**——数字在跳，说明刷新周期真的在跑，而不是屏幕冻在某一帧。
- **满 24 小时自动进位**：主数值从 `MM:SS` 变成 `59d23:59` 这种 `天 d 时:分` 写法，天数不会顶掉。第 5 页的分辨率更高（带秒），永远是绝对读数。
- **进度条 60 秒跑满一圈**：秒在走这件事，一条实心条比数字更容易一眼确认。

## 编译烧录

```bash
cd uptime-oled
pio run              # 编译
pio run -t upload    # 烧录（板子接 COM4，用板载原生 USB）
pio device monitor   # 串口监视 115200
```

零第三方依赖，只用 Arduino core 自带的 `Wire`。

## 串口输出长这样

```
=== uptime-oled ===
I2C: SCL=GPIO4  SDA=GPIO5  400000 Hz
OLED init OK, refreshing every 1s.
[0] uptime=00:00  refreshes=1
[1] uptime=00:01  refreshes=2
[2] uptime=00:02  refreshes=3
```

初始化失败时（屏幕不在线上）会打印 ASCII 版排查清单，并**每 5 秒自动重试**一次，
这样线没插好时插好就能自己恢复，不必重新上电：

```
[ERR] no ACK at 0x3C.
Check, in this order:
  1) SCL -> GPIO4 and SDA -> GPIO5 (swapped wires = no ACK)
  ...
[retry] probing OLED again...
```

日志刻意用 ASCII 而不是中文：中文经 UTF-8 送到部分串口工具会变成乱码，
而这条信息恰恰是出故障时唯一能看到的线索。

## 计时为什么用 `millis()`

需求是"显示通电时间"，精度要求 1 秒级：

- `millis()` 就是**自上电起**的单调计数（48 位累加，跑几十年不溢出），语义上正好等于"通电时间"，不需要额外维护 `startMillis`；
- 刷新判定用 `now - lastRefresh >= 1000`，**非阻塞**，没有 `delay(1000)`。将来加按键、传感器、网络都不用重构主循环；
- 刷新时间戳是 `lastRefresh += 1000` 而不是 `= now`，避免某次刷新被 I2C 拖长后误差长期累积。

> ⚠️ 注意：ESP32 进**深度睡眠**时 `millis()` 会停走，醒来后计时不包含睡眠时间。
> 本示例不涉及低功耗深睡。若将来要"跨重启/跨断电累计"，那需要 RTC 内存或 NVS 存储，是另一回事。

**实测**：连续采 45 秒串口日志，45 帧 / 45 秒 = **1.0000 帧每秒**，无漂移。

## 屏幕不在线上时不会拖垮计时

排查过程中发现一个真实的坑：`flush()` 要发 8 页 × 2 次 I2C 事务，
OLED 不在线时每次 `endTransmission()` 都会**阻塞到 50ms 超时**，
一轮刷新就是近 800ms —— 足以把 1 秒的节拍彻底带偏。

所以 `flush()` 在探测失败后直接返回（`if (!ok_) return;`），
主循环的计时精度与屏幕是否在线**完全解耦**。上面那组 1.0000 帧/秒的数据，
正是在 OLED 缺席的情况下测出来的，这也顺带证明了解耦确实生效。

## 诊断工具

`tools/` 下有两个独立小工程（各自 `platformio.ini`，单独编译烧录）：

| 工具 | 用途 |
|---|---|
| `tools/i2c-scan` | 扫 0x08–0x77，看总线上到底有没有器件、在哪个地址 |
| `tools/bus-probe` | 物理层体检：读 SCL/SDA 静态电平，判断是"没接"还是"被拉死" |

```bash
cd uptime-oled/tools/i2c-scan
pio run -t upload && pio device monitor
```

为什么单独放 `tools/` 而不是塞进 `src/`：同一个 `src/` 里出现两个
`setup()`/`loop()` 会直接链接失败，分开后两边都能单独编译。

## 常见问题

| 现象 | 排查 |
|---|---|
| 串口报 `no ACK at 0x3C` | ① SCL/SDA 是否接反；② VCC 是否真的 3.3V、模块电源灯是否亮；③ 裸屏需要外挂 4.7kΩ 上拉到 3V3（成品模块一般自带）；④ 地址是否为 0x3D。先跑 `tools/i2c-scan` |
| `i2c-scan` 每个地址都返回 `endTransmission=5` | 5 是**超时**而非"无应答"（无应答是 2）。全线超时说明总线被拉死或根本没接器件，跑 `tools/bus-probe` 读电平定位 |
| 全屏点亮/雪花 | 初始化序列没跑完就开始写数据，或电荷泵 `0x8D,0x14` 没发出去（3.3V 供电必须开内部电荷泵） |
| 画面左右或上下镜像 | 改 `CMD_SEG_REMAP` 的 `\|0x01` 位或 `CMD_COM_SCAN_DEC` |
| 屏亮但没内容 | 检查 `flush()` 是否被调用，以及是否忘了 `cmd(CMD_DISPLAY_ON)` |
| 字显示成乱块 | 字模取模方向必须与显存一致：**1 字节 1 列，bit0 = 页面最上一行**。`font5x7.h` 就是这个方向，另行替换字库时要对齐 |

### 本机实测记录（2026-10-14）

**首轮：接 GPIO1(SCL) / GPIO2(SDA)，OLED 在电气上完全不存在于总线上**

| 检查项 | 实测 |
|---|---|
| `pio run` | SUCCESS，0 warning，RAM 6.2% / Flash 8.5% |
| 烧录 | 成功，目标 ESP32-S3 (QFN56) rev v0.2 |
| 计时精度 | 45 帧 / 45 秒 = **1.0000 帧每秒** |
| 0x3C 探测 | 无应答 |
| `i2c-scan` 全段 0x08–0x77 | 每个地址 `endTransmission=5`（超时） |
| `bus-probe` GPIO1/GPIO2 | `pullup=HIGH float=HIGH` × 多轮 |

判读：两脚在"开内部上拉"和"纯悬空"两种状态下都读到 HIGH，且全部地址超时，
说明引脚处于**高阻态、外部没有任何器件在驱动或上拉**。

**次轮：改接 GPIO4(SCL) / GPIO5(SDA) → 一次点亮**

| 检查项 | 实测 |
|---|---|
| 0x3C 探测 | **应答**，初始化序列跑通 |
| 串口输出 | 无 `no ACK` 报错，计时逐秒递进 |
| 屏幕 | 正常显示 |

结论：GPIO1/2 与 GPIO4/5 都是 S3 的正常 IO，问题出在**当时那两脚确实没接通**，
与固件逻辑无关。完整硬件参数见仓库根目录 [`HARDWARE.md`](../HARDWARE.md)。

> 排查这类问题有个容易踩的点：`endTransmission()` 返回 **2**（地址无应答）和
> 返回 **5**（超时）含义完全不同。前者是"器件不在这个地址"，
> 后者是"总线根本没法完成事务"。看到 5 就不要再纠结地址了，直接查物理层。


## 不依赖 Adafruit_SSD1306 的原因

`src/ssd1306_i2c.cpp` + `src/font5x7.h` 是**裸驱实现**（约 200 行）：

- 自带 1KB 显存缓冲，只想"写文本 + 画一条进度条"这点需求，裸驱就够；
- 避免引入 GFX 抽象层和 Adafruit 的依赖树，编译更快、体积更小、改动完全可控；
- 初始化序列用的是 SSD1306 datasheet 的标准值；
- 零第三方依赖，只用 Arduino core 自带的 `Wire`。

分块传输是必须的：ESP32 的 `Wire` 单次事务缓冲约 128 字节，
而整帧是 8 页 × 128 列 = 1024 字节，所以 `flush()` 按页定位、
每页再切成 64 字节一块发送。

## 关于型号

屏幕型号是 **SSD1306** —— 128x64 OLED 最通用的经典款，0.96" / 1.3" 模块几乎都是它或兼容片。

驱动完全按 SSD1306 datasheet 编写：初始化序列是标准值，显存模型是 128 列 × 8 页。

> 首轮调试时型号曾被记作「SSD13159」，那是输入笔误。
> 该型号在任何厂商资料中都不存在，**实际就是 SSD1306**。
>
> 另：SSD1315 是 SSD1306 的引脚与命令兼容替代，同一套代码也能驱动它 ——
> 但本机这颗不同，确认是 SSD1306。
