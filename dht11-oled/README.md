# dht11-oled · DHT11 温湿度实时监测（128x64 OLED）

上电即开始采集，**每 1 秒**刷新一次屏幕，显示当前温度与湿度。
传感器是 **DHT11**（带灯模块），屏幕是 **SSD1306** 128x64 I2C OLED。
**零第三方依赖**：DHT11 时序与 OLED 驱动都是本仓库自写。

## 接线

| 器件 | 排针 | ESP32-S3 | 说明 |
|---|---|---|---|
| **DHT11** | **DATA** | **GPIO 7** | 用户指定：数据线接 7 号位 |
| DHT11 | VCC | 3V3 | DHT11 可 3.3V 供电 |
| DHT11 | GND | GND | |
| **OLED** | **SCL** | **GPIO 4** | |
| OLED | **SDA** | **GPIO 5** | |
| OLED | VCC | 3V3 | |
| OLED | GND | GND | |

> 引脚写在 `src/main.cpp` 顶部：`PIN_DHT_DATA` / `PIN_I2C_SCL` / `PIN_I2C_SDA`，换脚只改这几行。
> DHT11 与 OLED 用的是两组互不相干的引脚（DATA 是单总线，OLED 走 I2C）。

### 关于带灯模块的那颗灯

带灯版 DHT11 的灯是**模块自带的上拉/指示电路**，由模块 VCC 供电，恒亮。
它**不表示读到数据**——灯亮只说明模块通电了。判断程序有没有在跑，
看屏幕上每秒 +1 的刷新计数（第 6 页的 `#N`）。

DHT11 数据脚是**开漏 + 上拉**的单总线结构，模块板上自带 4.7k~10k 上拉电阻，
所以**不需要再外接上拉电阻**。裸传感器（没有模块板）才需要自己补一个。

## 屏幕布局

128x64 屏按 8 页（每页 8 像素高）组织，逐页说明：

```
┌────────────────────────────────┐
│ DHT11                     0s   │  ← 第 0 页：标题 + 右上角"数据年龄"
│ ────────────────────────────── │  ← 第 1 页：分隔线
│   ██ ██  ██                    │
│   ██ ██  ██                    │  ← 第 2~3 页：大号湿度（2 倍放大）
│   ██ ██  ██          0         │     （右下角小数字＝年龄，见下）
│ HUMIDITY %                     │  ← 第 4 页：大号数字的量纲
│ TEMP   32 C                    │  ← 第 5 页：温度明细
│ #1230                    ERR   │  ← 第 6 页：刷新计数 + 失败标记
│ OK  #1230                      │  ← 第 7 页：健康度 / 诊断
└────────────────────────────────┘
```

**大号数字给的是湿度，温度在第 5 页**：湿度变化更快，占大号位更直观；
温度是慢变量，用一行明细足够。若湿度失效，大号位降级显示温度
（第 4 页改写 `TEMP  C`），两个都没有时显示 `--`。

- **`#1230` 刷新计数**：每刷一屏 +1，是"1 秒更新一次"的现场证据。
  数字不变时看这个计数在跳，就知道程序活着而不是卡住了。
- **右上角 `0s` 是"数据年龄"**：刚刚采到新值时是 `0s`，采样失败后
  这个数会一秒一秒往上走，一眼看出屏幕上的数有多旧（上限 99s）。
  大号数字右下角另有一个同样的年龄角标，凑近看时不用抬头。
- **第 6 页右侧 `ERR`**：只在累计失败数 > 0 时出现，是个"曾经出过错"的标记。
- **第 7 页是诊断行**：接错线时直接显示是哪一种错，不用连串口。

## 实测结果

上机跑 20 秒，**19 次采样零失败**，温湿度都在动（对着传感器呼吸后
湿度从 79% 回落到 43%，温度 33 → 32°C），确认读的是真实传感器而非缓存：

```
t=1s,hum=79,temp=33,ok=1,fail=0      t=11s,hum=53,temp=33,ok=1,fail=0
t=5s,hum=69,temp=33,ok=1,fail=0      t=15s,hum=46,temp=32,ok=1,fail=0
t=10s,hum=55,temp=33,ok=1,fail=0     t=19s,hum=43,temp=32,ok=1,fail=0
```

编译占用：Flash 285,509 / 3,342,336 字节（8.5%），RAM 20,244 / 327,680 字节（6.2%），
`-Wall -Wextra` 下零警告。

## 串口输出

```
=== dht11-oled ===
DHT11: DATA=GPIO7 (self-written timing)  sample every 1000ms
OLED : SCL=GPIO4  SDA=GPIO5  400000 Hz
Screen refreshes every 1000ms.
DHT11 pin armed. Warming up...
OLED init OK.
[tick 1] no-data  age=0s  fails=0
t=1s,hum=40,temp=30,ok=1,fail=0
[tick 2] data  age=0s  fails=0
t=2s,hum=40,temp=30,ok=1,fail=0
```

两类行是分开的，别混看：

- **`[tick N]`** —— 每个屏幕刷新节拍打一次，报的是**当前读数状态**
  （`no-data` / `data`）、读数的**年龄**（`age=Ns`）和累计失败数。
- **`t=Ns,...`** —— 每次**采样**打一次，**成功失败都打**，是固定字段的 CSV：
  `t` 秒数、`hum` 湿度、`temp` 温度、`ok`（本次是否成功）、
  `fail`（累计失败次数）。

采样失败时 CSV 里的无效字段写 `--` 而不是 `0`——`0°C` 是合法读数，
写成 0 就跟"没读到"混在一起分不清了：

```
t=7s,hum=63,temp=24,ok=1,fail=0     ← 正常
t=8s,hum=--,temp=--,ok=0,fail=1     ← 本次失败，两个字段都是 --
```

成功行 `ok=1`、失败行 `ok=0`，所以直接 `grep -c 'ok=1'` 就能统计成功率。

上电后第一个 tick 是 `no-data` 属正常：程序会先空转
**`DHT_WARMUP_MS` = 1500ms** 等传感器供电稳下来，在这之前不采样。
所以 t≈1s 的第 1 个 tick 确实还没有读数，t≈2s 起进入 `data` 状态。

日志刻意用 ASCII 而不是中文：中文经 UTF-8 送到部分串口工具会变成乱码，而这条信息恰恰是出故障时唯一能看到的线索。

CSV 那几行可以直接丢进表格或脚本里做趋势。

## 为什么不用 Adafruit 的 DHT 库

**这是本项目实机踩到的坑，也是本仓库里最值得记的一条。**

初版就是用 `adafruit/DHT sensor library` 写的，实机表现为
**湿度正常、温度永远是 `--`**。根因出在库的接口设计上：

### 1. 它没有"读一次、拿温湿度两个值"的接口

DHT11 的 40 位是**一次不可分割的传输**，一次读就同时带回温度和湿度。
但库把原始字节 `data[5]` 设成了 `private`，也不提供读全部字段的入口，
调用方**只能**这样拿数据：

```cpp
float h = dht.readHumidity();     // 内部触发一次完整传输
float t = dht.readTemperature();  // 又触发一次完整传输
```

而 DHT11 两次转换之间要求 **≥1s**，同一秒里背靠背连调两次，
第二次必然读到失败/陈旧数据 —— `readTemperature()` 的校验和不过，
于是返回 `NAN`，屏幕就显示 `--`。**湿度能出来、温度出不来**正是这个原因：
调用顺序上湿度先读、拿到了有效值，温度后读、撞上了冷却期。

### 2. 它的超时是关中断自旋

`expectPulse()` 里是 `while (digitalRead(_pin) == level) {}`，且**中断已关**。
传感器不在线时会自旋到 ESP32 看门狗整板重启：

```
Guru Meditation Error: Core 1 panic'ed (Interrupt wdt timeout on CPU1)
```

**反复重启，连"传感器没接"这句诊断都来不及打印。**

### 现在的做法：自写时序（`src/dht11.h`）

两件事只用一个头文件解决，且不依赖任何第三方库：

- **一次传输解出全部 5 字节**，温湿度来自同一次读，不存在冷却期问题。
- **每个等待循环都有 cycle 上限**，任何一步超时都立刻返回错误码，
  **不可能自旋到看门狗**。

四个错误码对应四种物理故障，都会显示在屏幕第 7 页，让问题能一眼定位：

| 错误码 | 含义 |
|---|---|
| `DHT_ERR_NO_RESPONSE` | 发了起始信号，传感器没拉低应答 |
| `DHT_ERR_TIMEOUT` | 应答到了，但某位电平等不到边沿 |
| `DHT_ERR_CHECKSUM` | 40 位收齐了但校验和不对（多半是时序抖动） |
| `DHT_ERR_RANGE` | 校验和通过，但数值超出 DHT11 量程（元件坏了） |

### 两个精度上的事实，用之前要知道

- **只有整数，没有小数。** DHT11 的 40 位里 `data[1]` / `data[3]` 是
  温度/湿度的小数位，但**这颗芯片恒为 0**（DHT22 才有小数）。
  所以显示的是整数，分辨率就是 1°C / 1%RH。代码照收这两个字节但不用它。
- **量程判定用的是"精度保证范围"**，即 **20~90%RH、0~50°C**，
  而不是手册里那个更宽的"可测量范围"。也就是说读数一旦跑出这个区间，
  程序按 `OUT OF RANGE` 报错，而不是装作正常显示——
  这么做是因为 DHT11 在区间外本就无精度可言，报错比给个假数有用。

### 一个容易写错的地方：0/1 判据必须自校准

位判决**不能**拿"名义 50µs × `cyclesPerUs`"当阈值。原因是
`digitalRead()` 不是一条指令，循环体本身有开销，实测循环数被这个开销放大了，
**绝对阈值会比任何真实读数都大，导致 40 位全被判成 0**。

正确做法是比较**本位自己**的高、低电平实测宽度：
手册规定每位都是"50µs 低 + 变长高"，0 与 1 的低电平宽度相同——

```
0 -> 低 ~50µs，高 ~26µs   => 高 < 低
1 -> 低 ~50µs，高 ~70µs   => 高 > 低
```

所以 `if (highCycles > lowCycles) bit = 1;`。两个量都在同一环境实测，
循环开销被同时放大、比较时正好抵消，**与 CPU 主频无关**。

## 常见问题

| 现象 | 排查 |
|---|---|
| 屏幕显示 `NO SENSOR - CHECK DATA WIRE` | DHT11 的 DATA 没接到 GPIO7、模块没供电、或线断了。这是"摘掉内部上拉后线站不住"，即外部什么都没接 |
| 屏幕显示 `WAITING Ns` | 传感器在线但没回应。DHT11 上电后需要约 1.5 秒稳定时间，程序会自动等；`N` 是已等待的秒数，超过 10 秒仍无读数就查供电 |
| 屏幕显示 `NO RESPONSE` | 起始信号发下去了，器件没拉低应答。查 VCC（DHT11 要 3.3~5V）、以及 DATA 是否接成了别的脚 |
| 屏幕显示 `TIMEOUT` | 器件在应答但读到一半电平等不到边沿：数据线过长、接触不良、或旁边有强干扰 |
| 屏幕显示 `BAD CHECKSUM` | 40 位收齐了但校验和对不上，多半是时序抖动或干扰 |
| 屏幕显示 `OUT OF RANGE` | 校验和过了但数值离谱，元件坏了 |
| 湿度/温度偶尔跳一下 | DHT11 精度是 ±2°C / ±5%RH，且 1Hz 上限。本程序按 1 秒采样，已经到它的能力边界 |
| 屏幕全黑但串口正常 | 见 `uptime-oled/README.md` 的 OLED 排查表（SCL/SDA 接反、电荷泵、地址 0x3C/0x3D） |
| 串口一直报 `no OLED ACK` | 同上。DHT 采样不受影响，会照常继续 |

排查时也可以直接跑 `tools/dht-probe` 读 GPIO7 的裸电平，
绕开整个程序判断"传感器到底在不在"，比盯着屏幕猜快。需要的话串口
还会打印上表的四种错误各自的排查提示（只在状态变化时打，不刷屏）。

## 采样节拍与屏幕刷新都是 1 秒

需求就是 1 秒刷新，所以两个节拍都取 1s。相关常量都在 `src/main.cpp` 顶部：

| 常量 | 值 | 作用 |
|---|---|---|
| `TICK_MS` | 1000 | 屏幕刷新间隔（需求指定） |
| `SAMPLE_MS` | 1000 | 采样间隔（DHT11 的物理上限就是 1Hz） |
| `RETRY_MS` | 2000 | 采样失败后的重试间隔 |
| `DHT_WARMUP_MS` | 1500 | 上电空转，等传感器供电稳定 |
| `OLED_RETRY_MS` | 5000 | 屏幕掉线后的重新探测间隔 |

几个设计点：

- **采样 1s** 贴着 DHT11 的能力边界走。自写时序**不设**库那种
  "间隔不够就偷偷返回旧值"的机制——每次 `dht11Read()` 都真的碰硬件，
  失败就明确报错，不会拿旧值冒充新值。
- **失败后隔 2s 再试**而不是 1s：连续失败往往是接触问题，
  密采样没有帮助，只会让日志刷屏。
- **屏幕刷新与采样同步**，显示的是最近一次**成功**的读数；
  采样失败时屏幕保留上一次有效值，并在右上角显示年龄（秒），
  一眼看出屏幕上的数有多旧。
- **屏幕掉线会自愈**：每 5s 重新探测一次 OLED，接线插好后不必重新上电。

串口日志里 `ok` / `fail` 是两个累计计数器，能一眼看出长期运行的成功率。

## 计时为什么用 `millis()`

与 `uptime-oled` 同一套路：`now - lastTick >= 1000` 的非阻塞写法，
没有 `delay(1000)`；时间戳用 `lastTick += TICK_MS` 累加而不是 `= now`，
避免某次 I2C 传输拖长后误差长期累积。

```
dht11-oled/
```
