# status-oled

**版本 V1.0**

单屏幕显示 ESP32 自身状态。**不联网、不接传感器、无 secrets.h**，
上电即显，四个页面由 GPIO7 上的轻触按钮循环切换。

与同仓库的 `status-oled3` 的区别：那个是三屏 + PCA9548A + 阿里云服务器轮询
（M0 已编译、未上板）；本项目是**单屏、纯本地、零依赖**，两者并存。

版本号 `V1.0` 定义在 `src/config.h` 的 `VERSION_TEXT`，出现两处：

- 屏幕第 7 页（署名行的**最左侧**），四页都显示；
- 串口开机横幅 `=== status-oled V1.0 ===`。

> 改版本号时注意：它和第 7 页右端的 `SIUNGOLAI` 同行。署名固定从
> 列 74 起，所以版本号**最多 12 字符**（`12 × 6 = 72 < 74`）。
> 超了就会压到署名上——[tools/check_layout.py](tools/check_layout.py)
> 会独立复算这个间距并在相撞时报错。

## 硬件

| 项 | 值 |
|---|---|
| 板卡 | ESP32-S3-DevKitC-1 N16R8（16MB Flash + 8MB OPI PSRAM） |
| 屏幕 | SSD1306 128x64 OLED，I2C，7 位地址 `0x3C` |
| SCL | GPIO4 |
| SDA | GPIO5 |
| VCC / GND | 3V3 / GND |
| 按钮 | GPIO7 ↔ GND，轻触开关，无外部上拉（用内部上拉） |

接线按 HARDWARE.md §1.2、§2.3：GPIO1/2 的 I2C 本机全段超时不通，
GPIO19/20 是原生 USB 不能占，GPIO4/5 是实测可点亮的那一对。

### 与 dht11-oled 的冲突（重要）

GPIO7 同时是 `dht11-oled` 的 DHT11 数据脚。**两个项目同一时间只能插一个**：
本项目插按钮时把 DHT11 拔掉，反之亦然。原因是 DHT11 模块自带 4.7k~10k
上拉（HARDWARE.md §5.1），会和按钮要用的内部上拉并联，且模块的指示电路
可能驱动该线，让按键读数不稳定。

GPIO7 不是 ESP32-S3 的 strapping 脚（strapping 是 GPIO0/3/45/46），
做数字输入本身没有问题，冲突纯属"一个脚两个器件"。

## 屏幕内容

四页，每页 1 行页眉 + 5 行数据，底部留 2 行空白（P2 是例外，有 6 行数据）。

**列位规则**：标签左对齐顶列 0，数值右对齐贴列 20。

```
UP           00:03:02     ← 标签左，数值右，中间全是空档
HEAP    357K MIN 270K
CPU           240 MHz
```

数值起始列 = `21 − 数值长度`，所以**长数值左移、短数值右移**，四页翻页时
所有数值的右边缘对齐成一条竖线。`drawRow()` 用
`snprintf(line, ..., "%-4s%*s%s", label, pad, "", text)` 实现：
`%-4s` 输出标签（不足 4 列的补到 4 列），`%*s` 输出 `pad` 个空格，
`pad` 从**标签字段宽度**（`max(strlen(label), 4)`）起算，不是从 `strlen(label)` 起算。

> `%*s` 的宽度参数只作用于**它自己这个字段**。它后面还跟着一个 `%s`（数值），
> 所以宽度只能是补白数本身。若误写成 `pad + strlen(text)`，数值会被推出右边缘。
> 这是实际发生过并已修掉的缺陷（见变更记录）。

**唯一例外是 `MAC` 行**：它的数值 `12:34:56:78:9A:BC` 有 17 字符，
右对齐后起始列 = `21 − 17 = 4`，正好紧贴标签末尾，会读成
`MAC12:34:56:78:9A:BC`。所以这一行改用 `drawRowLeft()`，数值从第 5 列起，
**刻意不对齐**——MAC 有信息价值，宁可这一行破例，也不截断它。

全屏 21 行因此都恰好占满 21 列：右对齐的行是「标签 + 空档 + 数值」撑满，
`MAC` 行是全屏最长的数值本身撑满。

```
P1/4 OVERVIEW                 P2/4 IDENTITY
UP           00:01:23         CHIP      ESP32-S3 r0
HEAP    357K MIN 270K         MEM            16M+8M
CPU           240 MHz         MAC 12:34:56:78:9A:BC
RST          USB UART         SDK      v4.4.7-dirty
I2C           OK 0x3C         BOOT      017 RST 017
                              FLASH   281K/3264K 8%
V1.0                                             SIUNGOLAI
P3/4 HEAP                     P4/4 BUS
DRAM     24.0K/382.0K         I2C         SCL4 SDA5
FREE       358.0K 93%         FREQ          400 kHz
MIN        270.0K 70%         ADDR     0x3C SSD1306
MAX        150.0K 39%         SCAN             0x3C
FRAG              60%         LAST          3 s ago
V1.0                                             SIUNGOLAI
```

数值是运行时读数的示例，不是写死的常量。

> P2 是全屏唯一有 **6** 行数据的一页（其余三页各 5 行）。多出来的那行是
> `FLASH`，因为身份信息本身就有 6 项；它仍落在有效数据行内，不影响第 7 页署名。
>
> 第 7 页（最底 8 像素）是**左版本号 + 右署名**的固定页脚，四页都画，翻页不闪。

### 四页字段逐行含义

**P1 / OVERVIEW —— 现在怎么样**

| 行 | 含义 |
|---|---|
| `UP` | 开机到现在的运行时长（时:分:秒） |
| `HEAP` | 当前空闲堆 / 开机以来**最低**空闲堆。两个数并列是为了看出泄漏：单看当前值不知道有没有掉过；`MIN` 明显低于当前值才说明某段代码吃过内存 |
| `CPU` | 当前 CPU 主频。动态调频时这个数会变（本项目未启用调频，恒为 240 MHz） |
| `RST` | 上次复位原因（rom 原始值的友好名）。`USB UART` = 通过 USB 下载/复位，不是崩溃 |
| `I2C` | 屏幕自己还在不在线。`OK 0x3C` = 在，`ERR` = 掉线。拔 SDA 可复现 |

> P1 是唯一一页**全部是动态值**的页面，适合日常摆着当"这块板子活着吗"的指示器。
> `HEAP` 那行只给字节数不给百分比——百分比在 P3。

**P2 / IDENTITY —— 这块板子是谁**

| 行 | 含义 |
|---|---|
| `CHIP` | 芯片型号 + 晶圆版本（`r0` 是早期批次） |
| `MEM` | Flash + PSRAM 的**静态硬件容量**，上电后不会变 |
| `MAC` | eFuse 烧死的芯片唯一地址。**本文档与 `HARDWARE.md` 中的 MAC 一律是虚构示例**（统一用 `12:34:56:78:9A:BC`），真实值只在屏上与串口出现，不写进仓库 |
| `SDK` | Arduino-ESP32 核心版本。`-dirty` 是上游构建时工作区不干净的标记，非本项目产生 |
| `BOOT` / `RST` | 开机次数 / 复位次数。存在 RTC 内存，**真拔电归零**（见「已知限制」） |
| `FLASH` | 固件实际占用 / app 分区容量 / 百分比 |

> `FLASH` 的分母是 **app0 分区（3264K）**，不是芯片的 16MB。程序只能装进 app 分区，
> 拿 16MB 当分母会得到 1.7% 这种没有意义的数。
>
> 分子（`ESP.getSketchSize()`）与编译期统计的 `firmware.bin` 大小会差几百字节：
> 前者是各段之和，后者含镜像头与对齐填充。两个数都对，口径不同。

### P3 堆详情怎么读

P3 的五个数不是四个孤立的读数，而是一组诊断：

| 行 | 含义 |
|---|---|
| `DRAM` | **已用 / 总量**。分数形式，把「已用的量」和「基数」放同一行 |
| `FREE` | 当前可用 + 占 DRAM 的百分比 |
| `MIN` | 开机以来**最低**可用值（历史水位） |
| `MAX` | 当前能一次性申请的**最大连续块** |
| `FRAG` | 碎片率 = `(DRAM − MAX) / DRAM` |

**关键是 `MAX` 和 `FREE` 的落差。** 可用 358K 却只能连续申请 150K，
说明内存被切碎了——`FRAG` 就是把这个落差量化成一个数。
`FRAG` 越高越糟：0% 表示完全连续。

> 四个百分比（`FREE` / `MIN` / `MAX` / `FRAG`）**一律以 `DRAM` 为分母**，
> 全页同一参照系，一行行读下来不用换算分母。
>
> `MAX` 不是 `MIN` 的补数：`MIN` 是历史最低水位，`MAX` 是当前最大连续块。
> 两个都小才是内存真的紧；只有 `MAX` 小而 `FREE` 大，那才是碎片化。
> P1 的单行 `HEAP` 看不出碎片，这是 P3 存在的理由。
>
> P3 刻意**不放堆横条**：堆每秒都在跳变，横条会跟着抖，反而看不清。

### P4 总线详情怎么读

| 行 | 含义 |
|---|---|
| `I2C` | 引脚分配：`SCL4 SDA5` = GPIO4 时钟 / GPIO5 数据 |
| `FREQ` | 当前总线速率（本项目 400 kHz） |
| `ADDR` | 屏幕**实际应答**的地址。主地址 0x3C 失败会回退 0x3D，这里显示生效的那个 |
| `SCAN` | 总线上所有应答的地址（最多列 3 个，见下） |
| `LAST` | 距上次总线扫描的秒数。每 10 秒静默重扫一次 |

`ADDR` 和 `SCAN` 的区别：`ADDR` 是驱动**正在对话**的那个从机（会随地址回退变化），
`SCAN` 是**全总线普查**的结果（无论驱动有没有在用它）。单屏场景两者应始终一致；
若 `SCAN` 出现 `ADDR` 之外的地址，说明总线上还挂着别的器件。

排查接线时先看这一页：拔掉 SDA 会立刻变成 `ADDR no reply` / `SCAN none`，
插回 5 秒内自愈，不需要重新上电。

### 页脚：版本号 + 署名

四页的第 7 页（屏幕最底部 8 像素）都不放数据，整行空闲，用作固定页脚：

| 位置 | 内容 | 起点 |
|---|---|---|
| 左端 | 版本号 `V1.0` | 列 0（左对齐） |
| 右端 | `SIUNGOLAI` 署名 | 列 74（右对齐贴边） |

两串都用普通 5x7 字模，与页内数据同字号，四页都画，翻页时不会闪。

**署名**占 9 字符 × 6 列 = 54 列：

- 起点 `LOGO_X = 74`；
- 末字符实体占列 122..126，其字间距占列 127，**正好贴边，一个像素不浪费**。

> `LOGO_X` 是算出来的不是调出来的。**改 `LOGO_TEXT` 的字符数就必须重算 `LOGO_X`**，
> 否则末字符会被 `drawText5x7` 的越界保护整字丢弃。
> [tools/check_layout.py](tools/check_layout.py) 会独立复算这个值并在对不上时报错。

**版本号**在左端，与水印同行的代价是**长度受限**：

- 署名从列 74 起，所以左侧只有 `74 / 6 = 12` 列可用；
- 当前 `V1.0` 占 4 字符 = 24 px，与水印间隔 50 px，很宽裕；
- **超过 12 字符就会压到署名上**，脚本会报错拦下。

> 版本号只此一处（加串口横幅），**不做两处定义**——避免代码里一个值、
> 文档里另一个值这种最常见的不一致。改就改 `config.h` 的 `VERSION_TEXT`。

曾经试过"只取字模低 4 位"的半高画法想让署名更小，实际渲染后发现
5x7 字模的辨识特征集中在下半部，砍掉后 `O` 与 `G`、`S` 与 `C`、`U` 与 `N`
互相混淆，故放弃。渲染验证见本文末尾的变更记录。

### 按键

| 动作 | 效果 |
|---|---|
| 短按 | 翻到下一页，P4 再按回 P1 |
| 上电时按住 ≥1.5s 再松手 | 跑字模方向自检（两条 1x4 竖条，停 6 秒） |

数值每 1 秒刷新一次，翻页立即重绘不等节拍；页面停住但数值照走。

按键累计次数只写在串口日志里（`[btn] pressed: page -> P2/4  (K=1)`），
不上屏——页眉留给页名，屏面留给状态。

> **自检要等屏幕先上线**。按住判据在 `display.begin()` 成功之后才采集，
> 屏幕没应答时不会进那段 6 秒阻塞（否则屏是黑的，空等 6 秒什么也看不到）。
>
> **`SCAN` 行最多列 3 个地址**。数值列宽 17 字符，每个地址占 5 字符加 1 空格，
> 第 4 个就会超出屏幕 21 列——此时宁可少列一个也不画半截。
> 单屏场景只有 SSD1306 一个从机，正常情况恒为 1 个地址。

### 屏幕掉线与自愈

固件把"屏幕在线"当成一个**运行期持续判定**的状态，而不是一次性的开机结论。
三处配合保证掉线能被发现、也能自愈：

1. **I2C 返回值全部检查**。`cmd()` / `cmd2()` / `probe()` / `flush()` 的
   `Wire.endTransmission()` 返回码不再丢弃。初始化途中任何一条命令得不到
   ACK，`begin()` 直接返回 false，不谎报"已就绪"。
2. **运行期掉线检测复用 flush() 自己的事务**。`flush()` 本来每帧就要发
   8 页 × 2 = 16 次数据事务；驱动数这些事务里有几次拿到了 ACK，
   **不额外插入任何探测事务**——否则会把 1 秒节拍推向饱和。
   判据是"连续 `kOfflineFlushFails`(=2) 次整帧全部失败"才算掉线：
   单次 NACK 属正常抖动，不清 `ok_`；任意一次成功立即清零计数并可自愈。
   按 1 秒节拍约 2 秒确认掉线。
3. **掉线期间总线扫描照常跑**。`loop()` 在 `!display.ready()` 时不提前
   `return`，10 秒重扫与 `LAST` 计时继续工作——扫描是独立诊断手段，
   不依赖 OLED 在线；若跳过它，屏上 `LAST` 会冻结在掉线那一刻，
   恰好丢掉排查掉线最需要的现场。

重连成功后 `lastRefresh` 会对齐到当下（`lastRefresh = now`），
避免掉线 30 秒后累加式一次只加 1000、连续几十轮全速重绘。

> 地址回退是无状态的：`begin()` **每次**都从 `OLED_ADDR_PRIMARY`(0x3C)
> 重新试探，用局部变量承载结果，只有探通了才写回生效地址。
> 因此"某次上电时序 / 接触不良导致 0x3C 瞬时探测失败"不会把地址永久
> 锁死在 0x3D——下一次重试仍会先试 0x3C，可自愈。

### 按键判读（消抖 30ms）

按钮没有外部上拉电阻，所以用 `INPUT_PULLUP`：平时读到高电平，
按下接地读低。判读用 `millis()` 状态机而不是 `delay()`，不阻塞主循环：

1. 读到低电平，记下时刻，等 30ms 让抖动过去；
2. 30ms 后仍为低电平才认定"真的按下"，翻页并重绘；
3. 松开沿不翻页，必须重新按一次。

抖动窗口内不做任何表态，所以按住不放只翻一页，不会连翻。

### 串口输出

每秒一行，与屏上 P1 同源；按键、翻页、总线重扫、屏幕掉线各有一行事件行。

```
=== status-oled V1.0 ===
chip ESP32-S3 rev0  flash 16777216 bytes  psram 8386295 bytes
MAC 12:34:56:78:9A:BC
SDK v4.4.7-dirty
app partition 3342336 bytes  sketch 288208 bytes
reset reason 0 (USB UART)  boot#17  rst#17
OLED online at 0x3C
startup done, uptime base 367 ms
P1  UP 00:00:01  HEAP 357/382K  CPU 240MHz  RST USB UART
[btn] pressed: page -> P2/4  (K=1)
[bus] rescan: 1 addr(s)
```

> 上面这行 `reset reason 0 (USB UART)` 是本机实测原样：**前面那个 `0` 是 IDF 的
> 枚举值（`ESP_RST_UNKNOWN`），后面括号里才是补判后的真实原因**。这不是笔误，
> 是 ADR 0005 记录的那个坑的现场证据。
>
> `psram 8386295 bytes` 而不是 8388608，少的那 1 字节（以及 heap 口径的差额）
> 是 IDF 自己预留的，不是检测失败。补 `-DBOARD_HAS_PSRAM` 之前这里是 `0 bytes`，
> 详见「已知限制」与 [HARDWARE.md §1.3.1](../HARDWARE.md)。

串口是唯一可独立验证的参照物：屏上显示的每个值都应在串口有对应字段。
两边不一致就是 bug，不是"屏幕有延迟"。

### 串口优先于屏幕排障

屏幕只有 21x5 字符，出错时信息量不够；而且屏幕本身坏了的时候，屏幕上的错误提示
恰恰是你唯一看不到的东西。所以每一轮验证都按这个顺序：

1. **先看串口**每秒那行 —— 判断固件是否活着、节拍是否准、读数是否合理；
2. **再看屏幕** —— 只用来确认"屏上画的和串口报的一致"。

如果屏幕全黑而串口正常，问题在 I2C 接线或屏幕本身，不在固件。

### `RST UNKNOWN` 是本机必经的坑（已修）

用原生 USB 复位（`pio run -t upload` 之后的 hard reset、串口工具拉 DTR/RTS）时，
ESP32-S3 的 rom 层给出 `RESET_REASON_CORE_USB_UART = 0x15`，
但 IDF 的 `esp_reset_reason_init()` 里那张映射表只编到 `0x12`，
`0x13`~`0x17` 全部掉进 default 分支变成 `ESP_RST_UNKNOWN`，
于是屏上永远显示 `UNKNOWN`，看着像固件坏了。

本项目直接读 rom 原始值补判，USB 复位显示 `USB UART` / `USB JTAG`。
只有真拔电重插才会看到 `POWERON`。细节见本文件「设计取舍」节。

## 已知限制

- **RTC 复位计数掉电即丢**。真拔电后计数归零；软复位 / 看门狗复位保留。
  首次烧录后 RTC 是垃圾值，所以有 magic 校验（`STA1`）兜底。
  要跨掉电累计得写 NVS，本项目不做（见「设计取舍」节）。
- **`ESP.getPsramSize()` 恒返回 0 的坑（本项目实际踩过并已修）**。
  本板有 8MB OPI PSRAM，但 `board=esp32-s3-devkitc-1` 在本机 platform 7.1.3 下
  解析成 `ESP32-S3-DevKitC-1-N8 (8 MB QD, No PSRAM)` 变体，导致 Arduino 的
  `psramFound()` 被编译成恒返回 0 的桩，`ESP.getPsramSize()` 于是永远报 0
  —— 而 IDF 其实已把 PSRAM 加进堆，`heap_caps_malloc(MALLOC_CAP_SPIRAM)`
  能正常分配读写。症状是屏上 `MEM 16M+8M` 会错误地显示成 `16M+0K`。
  修法是 `platformio.ini` 的 `build_flags` 加 `-DBOARD_HAS_PSRAM`。
  **注意 `board_build.arduino.memory_type=qio_opi` 管不到这件事**：它只决定
  链接期内存布局，`BOARD_HAS_PSRAM` 是编译期运行标志，两者必须同时存在。
  完整推导（含反汇编证据）见 [HARDWARE.md §1.3.1](../HARDWARE.md)。
- **SDK 版本可能带 git hash**（例如 `v4.4.7-38-g38eeba21`），超 17 字符会被
  截断。本项目实测是 `v4.4.7-dirty`，13 字符，截断不会发生。
- **总线扫描最坏约 5.6 秒**。从机不在线时每次 `endTransmission` 等满 50ms
  超时，112 个地址全无应答就要等 5.6 秒。所以扫描只在启动时和之后每 10 秒
  各做一次，且不触发重绘；按钮翻页随时可打断等待感（扫描在主循环外单独跑，
  翻页仍即时）。这是 HARDWARE.md §6.2 那条"下游器件不在线时不要刷新"的翻版。
  **屏幕掉线期间扫描照常进行**——它是独立诊断手段，不依赖 OLED 在线。
- **`Wire.setTimeOut(50)` 的实际超时语义未经实测**。实装链路是
  `Wire.cpp:398-401`（只存成员）→ `Wire.cpp:453`（作为 `_timeOutMillis`
  传入）→ `esp32-hal-i2c.c:176`
  （`i2c_master_cmd_begin(..., timeOutMillis / portTICK_RATE_MS)`）。
  实际超时 = `50 / portTICK_RATE_MS` 个 tick，取决于本 core 的
  `CONFIG_FREERTOS_HZ`。上面"5.6 秒"和"8 页拖住近一秒"两个量化结论都
  建立在这个前提上，属未复核假设（`Wire.setTimeOut(50)` 的真实超时语义
  尚未在板上实测，未写进本文档，见「设计取舍」节的未复核项说明）。

### 排版自检

`tools/check_layout.py` 在主机上复刻 `drawRow()` 和四个页面的拼串逻辑，
逐行核对两件事：

1. 每行不超过 21 列（128px / 6px 的硬上限，超了右边缘字符会被切掉）；
2. 每个标签都在 README 的 ASCII 框图里出现过（防止改了代码忘了改文档）。

```powershell
python status-oled/tools/check_layout.py
```

这不能替代上屏目视，但能挡住"字串拼太长"这类只有把屏凑近才看得出的问题——
本项目的屏幕框图和代码是两处独立维护的同一份事实，这个脚本是它们之间的对账。

### 相对 uptime-oled 的改动

`ssd1306_i2c.{h,cpp}` 逐字复制自 `uptime-oled/src/`，刻意保留三处差异：

1. **`begin()` 不再自动调用 `fontDirProbe()`**。uptime-oled 每次上电都要等
   6 秒字模自检；本项目要求上电即显，自检改成"按住按钮 ≥1.5s 才跑"。
2. **`begin()` 做主/备地址回退**。uptime-oled 声明了 `OLED_ADDR_ALT = 0x3D`
   却从未使用；本项目真正实现了"0x3C 无应答就试 0x3D"，
   且回退是无状态的——每次 `begin()` 都从主地址重新试探，不会锁死。
3. **所有 I2C 返回值都被检查**。`cmd()` / `cmd2()` 由 `void` 改为返回 `bool`，
   运行期掉线可被感知（见上文「屏幕掉线与自愈」）。

另加 `address()` getter，让 P1/P4 显示驱动实际生效的地址，
避免屏上写 `0x3C` 而实际连的是 `0x3D`。

`font5x7.h` 逐字复制，未改。

`main.cpp` 是新写的，但主循环范式照抄 `uptime-oled/src/main.cpp`：
纯 `millis()` 非阻塞、`lastRefresh += REFRESH_MS` 累加防漂移、
屏幕掉线每 5 秒重试 `begin()`。

## 设计取舍

本节内联了本项目的关键决策与理由，**不依赖任何外部文件**。
（`docs/` 下的 ADR 与审查报告被仓库根 `.gitignore` 的 `/status-oled/docs/`
规则忽略，只存在于本地，见「代码结构」节的说明。）

| 决策 | 取舍 |
|---|---|
| **不联网、只显示本地状态** | clock-oled 已覆盖「联网 + NTP + RSSI」；WiFi 会让 RAM 从 6.2% 涨到 14.1%、Flash 从 8.5% 涨到 21.5%，还要引入 `src/secrets.h`。本项目要的是"上电即显、零配置"，故不联网 |
| **手动翻页，不做自动轮播** | 自动轮播会在你想盯住某一页时把画面切走；按钮翻页让页面停住，但**数值仍每秒更新** |
| **复位计数用 `RTC_NOINIT_ATTR`，不用 `RTC_DATA_ATTR`** | `RTC_DATA_ATTR` 落在 `.rtc.data` 段，**该段不是 NOLOAD**，启动时会被 flash 映像里的初值覆盖，计数每次上电都归零、完全失去意义；`.rtc_noinit` 是 NOLOAD，软复位 / 看门狗复位后保留。代价：**真拔电即丢**，故配 magic 校验（`STA1`）兜底首次烧录后的垃圾值 |
| **复制 SSD1306 裸驱，不抽共享库** | 抽公共库属于重构，会动到 `uptime-oled` / `clock-oled` 这些**已验证并上板过的项目**。本项目选择复制 + 记录三处差异，把风险限制在新项目内 |
| **补判 USB 复位原因 `0x13–0x17`** | IDF 的 `esp_reset_reason_init()` 内部 switch 只映射到 `0x12`，`0x13–0x17` 全落进 `default` 变成 `ESP_RST_UNKNOWN`。本机用原生 USB 复位是常态，不补判屏上会一直显示 `UNKNOWN` |
| **`MAC` 行是全屏唯一左对齐行** | 该行数值 17 字符，右对齐后起始列 = `21 − 17 = 4`，会紧贴标签读成 `MAC12:34:56:78:9A:BC`。宁可这一行破例，也不截断 MAC |

**未复核项**（已知成立性未在板上实测，本文档不作断言）：

- `Wire.setTimeOut(50)` 的真实超时语义。它最终走到
  `i2c_master_cmd_begin(..., timeOutMillis / portTICK_RATE_MS)`，
  实际超时 = `50 / portTICK_RATE_MS` 个 tick，取决于本 core 的 `CONFIG_FREERTOS_HZ`。
  本文件「已知限制」里"5.6 秒"和"8 页拖住近一秒"两个量化结论都建立在这个前提上。
